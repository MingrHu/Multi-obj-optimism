# 优化工作流前三项改进 ExecPlan

本计划是活文档。实施期间持续更新 `Progress`、`Surprises & Discoveries`、
`Decision Log` 和 `Outcomes & Retrospective`，使后续开发者只阅读本文件也能继续工作。

## Purpose / Big Picture

优化工作流需要从“一次性提交表单”提升为可追溯、可校验的工程工具。完成后，同一个 DOE
可以保留多次优化运行及各自结果；用户可以查看版本摘要并重新加载任一历史结果。目标方向和
权重不再依赖任意文本，设计变量边界在提交前即时显示错误和训练范围风险。

## Surprises & Discoveries

- `store.register_resource()` 原先会删除同类型旧资源，因此仅在优化状态中追加历史记录不足以
  保留旧结果；必须同时调整资源保留策略并为每次运行使用独立目录。
- 优化工作线程会从传入请求中 `pop("optimizer")`，历史记录必须在启动线程前持久化 JSON 副本，
  不能把运行中的可变字典直接作为历史来源。
- 结果页原先只按 DOE 顶层 `stage=optimization_finished` 过滤；最近一次运行失败会掩盖更早的
  完成结果。列表摘要新增 `has_optimization_result` 后，可以继续访问已有历史版本。

## Decision Log

- Decision：运行版本使用服务端生成的 `run_id`，每个 DOE 下唯一。
  Rationale：底层 `optimization_id` 只有算法真正启动后才生成，无法代表排队、失败或中止运行。
- Decision：保持现有优化查询接口并扩展 `history/current_run_id`，不新增重复的历史路由。
  Rationale：当前桌面端已经轮询该接口，兼容旧客户端且减少协议入口。
- Decision：旧 DOE 没有 `history` 时，把当前 `request/result` 作为兼容的单一历史版本展示。
  Rationale：避免部署升级后历史任务突然无法读取。
- Decision：多目标模式保留权重字段但注明不参与 NSGA-II 多目标排序；单目标和强化学习要求
  权重非负且总和为 1。
  Rationale：与当前后端校验规则一致，不改变算法定义。

## Plan of Work

首先扩展 `mobo.api.store/service`：提交优化时创建运行记录，状态变化同步到当前记录；每次运行的
文件复制到 `optimization/<run_id>/`，优化资源注册不替换旧资源。查询接口返回当前运行标识和
按时间排列的历史记录。

然后更新 PySide6 优化中心：给目标方向、权重和边界列安装结构化编辑器；表格改变时运行统一
校验，错误行高亮并显示可执行提示。加载训练模式时保留训练上下界，用于越界警告。

最后更新结果分析：加载 DOE 时展示全部历史运行摘要；默认结果仍可查看，同时允许选择并加载
任一已完成版本。补充协议、测试和 Docker 验证。

## Validation and Acceptance

1. 连续提交两次优化后，查询响应包含两个不同 `run_id`，两个结果资源均可读取。
2. 历史结果文件位于不同运行目录，新运行不覆盖旧文件。
3. 方向编辑器只能选择 `min/max`；权重和边界编辑器只接受数值。
4. 下限不小于上限时行被标红且不能提交；超出训练范围时显示警告但允许用户确认配置。
5. 结果页能展示运行摘要并加载指定历史版本。
6. `pytest` 定向测试、Ruff、`tools/check_docs.py` 和 Docker 健康检查通过。

## Outcomes & Retrospective

前三项已完成。优化提交响应提供 `run_id`，查询响应提供 `current_run_id/history`；每个版本的
结果文件保存在 `optimization/<run_id>/`，资源注册不再删除旧优化资源。结果页能比较运行状态、
模式、算法、解数量、耗时和更新时间，并加载任一完成版本。

目标方向和数值字段已使用 Qt 委托限制输入。即时校验覆盖重复名称、方向、权重范围及总和、
上下界关系和训练范围越界。多目标权重明确标识为记录信息，不改变 NSGA-II Pareto 排序。
